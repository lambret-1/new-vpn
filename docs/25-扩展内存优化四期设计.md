# 25 - VPN 隧道扩展内存优化四期设计方案

> 适用对象：`Sources/TunnelExtension`（PacketTunnel 扩展进程）及其与主 App 的 App Group 通信。
> 目标：在不牺牲诊断能力的前提下，把扩展常驻内存压到 jetsam 阈值以下，消除长时运行后的内存爬升与偶发 Jetsam 杀进程。
> 约束：纯原生 Swift / Objective-C，最低 iOS 16，不引入跨端库；libbox v1.11.0 白名单字段内配置。
>
> **范围排除**：MITM 中间人、HTTP 抓包相关模块（`MITM证书签发器`/`MITM连接处理器`/`本地HTTP代理`/`抓包存储管理器`）当前尚未启用、暂不投入使用，本方案**不纳入优化范围**；后续这些功能真正落地时再单独立项。本方案只针对当前真实在跑的核心链路：TUN 隧道、sing-box Go 内核、隧道日志、DNS 记录、连接记录、内存采样与 App Group 通信。

---

## 0. 现状基线（已做过的优化）

| 位置 | 现状 | 文件 |
|------|------|------|
| Go 堆 | `GOGC=20`、`GOMEMLIMIT=32MiB` 硬编码 | `SingBox内核桥接.swift:116-117` |
| DNS 查询计时表 | 15s 超时清理 | `PacketTunnelProvider.swift:597-606` |
| 隧道日志环形缓冲 | 上限 200 条，全量 JSON 编解码 | `PacketTunnelProvider.swift:1065-1077` |
| DNS 记录 | 上限 200 条，`[[String:Any]]` 整表读写 | `PacketTunnelProvider.swift:926-934` |
| 连接记录 | 上限 100 条 | `PacketTunnelProvider.swift:980-995` |
| 内存采样 | 独立 1s 定时器，每秒 `set`+`synchronize` | `PacketTunnelProvider.swift:669-687` |
| 流量统计 | 另一个 1s 定时器，写 5 个键 + `synchronize` | `PacketTunnelProvider.swift:590-634` |
| 清理触发 | **仅手动**：主 App 写命令戳，扩展每秒轮询 | `PacketTunnelProvider.swift:690-733` |
| 背压 | 日志积压 >100 丢弃调试日志 | `PacketTunnelProvider.swift:1049` |

**结论**：限流和上限做了，但缺三样东西——①不知道内存到底花在哪；②没有按内存压力自动降级；③热点通路上仍在做 O(n) 整表重写。

## 一期：内存画像与可观测性（先测量，再动手）

### 目标
建立扩展进程的内存分桶画像，定位真正的大头，避免拍脑袋改阈值。

### 改造点

1. **扩展端新增「内存分桶采样」**（`PacketTunnelProvider`）
   - 复用现有 1s 采样定时器，在写 `tunnelMemoryBytes` 的同时，统计并写入一组轻量指标到 App Group：
     - `memBucketLogs`：当前隧道日志数组条数 + 上次 JSON 编码字节数
     - `memBucketDns`：DNS 记录条数
     - `memBucketConn`：连接记录条数
     - `memBucketDnsTimer`：DNS 查询计时表当前条数
     - `memBucketGoroutine`：通过 libbox 平台接口可读的 Go 侧句柄数（取不到则上报 -1）
   - 这些都是 `Int`，每次写一个小字典，不带大对象，成本可忽略。

2. **接入系统内存压力源**
   - 新增 `DispatchSource.makeMemoryPressureSource(eventMask: [.warning, .critical], queue:)`，在 `startTunnel` 启动、`stopTunnel` 取消。
   - 压力事件触发时，记录一条结构化日志（含当前 resident 字节、各分桶条数），作为后续自动降级的信号源。
   - 同时用 `os_proc_available_memory()`（iOS 13+）做一次主动阈值探测，补 `task_info` 只看 resident 的盲区。

3. **手动清理升级为「清理前后对比埋点」**
   - 现有 `检测并执行内存清理` 在清理前/后各记一次 resident 与分桶，写回 App Group，主 App 可看到「清理释放了多少」。

### 验收
- 主 App 网络活动页能看到：总 resident + 各分桶条数（日志/DNS/连接/计时表）+ 最近一次压力事件时间。
- 连续跑 30 分钟高流量后，能明确指出内存增长主要来自哪 1~2 个分桶。

### 风险
- 压力源回调在 utility 队列，不得在其中同步做重活；只置标志位 + 记日志。

## 二期：App Group 通信通路减负（热点 O(n) → O(1)）

### 目标
消灭「每来一条日志/一条 DNS 记录就把整张表解码、插入、再编码写盘」的热点。

### 改造点

1. **合并双 1s 定时器**
   - 现有「统计定时器」和「内存采样定时器」都是 1s、都 `synchronize()`。合并为一个 `状态上报定时器`：一轮里依次写流量字节、resident、分桶指标、轮询清理指令。
   - `synchronize()` 从每秒 2 次降到 1 次；非关键键去掉 `synchronize`，仅在隧道状态翻转（连接/断开）时 `synchronize`。

2. **隧道日志：整表重写 → 增量追加文件**
   - 现状（`PacketTunnelProvider.swift:1065-1077`）：每条日志都 `JSONDecoder` 解 200 条 → 插入 → `JSONEncoder` 再编码 → 写 UserDefaults。日志密集时这是 O(n²)。
   - 改为：扩展侧维护一个内存 `[条目]` 环形缓冲（上限 200，纯内存，不落 UserDefaults）；
     每 5 秒批量编码一次写 App Group 文件（`tunnelLogs.json`），而不是每条写；
     后台时进一步降为 15 秒或直接不写。
   - 日志写盘动作从「每条一次」变成「每 5 秒一次」。

3. **DNS 记录 / 连接记录：去掉整表 `[[String:Any]]` 重写**
   - `保存DNS记录`（`PacketTunnelProvider.swift:926-934`）和 `解析并记录连接`（:980-995）每次都读整表、insert、写整表。
   - 改为扩展侧内存环形缓冲去重合并（域名+类型为键），批量每 2~3 秒刷一次 App Group；主 App 端只读快照。
   - 去重逻辑（同域名多 IP 合并）下沉到扩展内存侧，主 App 不再 decode 后再合并。

### 验收
- 高日志频率下，扩展 CPU 占用明显下降（对比一期埋点）。
- 每秒 `synchronize` 次数 ≤1。
- UI 看到的日志/记录延迟可接受（≤5s 刷新，调试场景够用）。

### 风险
- 批量写意味着扩展被 jetsam 强杀时可能丢最近几秒日志——可接受（调试数据，非业务数据）。
- 必须保留「主 App 立即拉取」时的一次性全量读路径。

## 三期：压力驱动的自动降级（从手动清理到自动保命）

### 目标
扩展被系统 jetsam 杀之前，自己先丢非关键数据，把 resident 压回安全线。

### 阈值（按 resident resident_size 分档）

| 档位 | resident 区间 | 动作 |
|------|----------------|------|
| 正常 | < 18 MB | 无 |
| 警告 | 18 ~ 26 MB | 日志级别压到「警告及以上」；清空 DNS 记录内存表与连接记录表；Go 侧主动触发一次 GC |
| 危险 | 26 ~ 32 MB | 进一步清空 DNS 查询计时表；隧道日志环形缓冲从 200 条收紧到 80 条；暂停非关键调试日志落盘 |
| 致命 | > 32 MB（触顶 GOMEMLIMIT） | 记录致命日志后，主动优雅断开并让系统重连（`reassert` 触发重启扩展，相当于自救） |

### 改造点

1. **统一「内存降级策略器」**（扩展侧新对象）
   - 输入：一期的 resident 采样 + 压力源事件。
   - 内部按上面档位做状态机，档位只升不降（ hysteresis：降档要回到「正常」并稳定 30s 才恢复）。
   - 每个动作幂等、可重复调用；只清理诊断类数据（日志/DNS/连接记录），不碰 TUN 与内核连接表。

2. **接 Go GC**
   - libbox 若暴露 runtime GC 触发接口则调用；否则通过「释放 Swift 侧大对象 + 等下个 GOGC=20 周期」间接达成。在文档中标注此为 best-effort。

3. **主 App 可视化**
   - 把当前档位（正常/警告/危险/致命）和最近一次自动降级原因写入 App Group，`VPN扩展内存监控器` 展示一个「自动降档」徽标，替代现在的纯数字。

### 验收
- 压测（大量短连接 + 高频 DNS 解析）下，resident 触及危险档后自动回落，不再一路涨到 jetsam。
- 断流时网络仍可用（降级动作不杀 TUN、不清内核连接表）。

### 风险
- 降档过快会让用户看到「日志突然没了」。用日志明确记录「因内存压力进入 X 档」。
- 致命档主动重连要确保只在连续 2 个采样周期超阈值才触发，避免抖动重连。

## 四期：Go 内核治本与长时稳态

### 目标
消除长时运行的残余增长大头：Go 堆/缓存文件调优、诊断数据结构容量上限、潜在泄漏点。

### 改造点

1. **libbox 配置侧**（`SingBox配置生成器`，严格在白名单内）
   - `experimental.cache_file`：限定 `enabled` + `store_fakeip`，并设置合理 `cache_file_id`；不使用任何白名单外字段。
   - 按设备物理内存自适应 `GOMEMLIMIT`：低端设备 24MiB、中端 32MiB、高端 48MiB，替换硬编码 32MiB（`SingBox内核桥接.swift:117`）。
   - DNS `strategy=ipv4_only` 等已支持项确认开启，减少 IPv6 双份记录的内存放大。

2. **诊断数据结构容量上限**
   - 扩展侧自行维护的 DNS 查询计时表、DNS 记录表、连接记录表全部带硬容量上限与 LRU 淘汰，超容量淘汰最旧；一期分桶会暴露它们的条数。
   - 容量上限随三期档位动态收紧（正常档 200、危险档 80）。

3. **泄漏审计清单**
   - 静态扫一遍扩展侧：`Timer`/`DispatchSourceTimer` 是否都有对应 `invalidate`/`cancel`；闭包是否 `[weak self]`；字典/数组增长点是否都有上限。
   - 重点核对两个 1s 定时器、DNS 日志解析路径上的异步块是否存在循环引用或只增不减的集合。

### 验收
- 连续运行 2 小时 + 周期性切换网络，resident 进入稳态（不再单调爬升），三期降档动作次数趋近于 0。
- 高频 DNS / 短连接压测下，扩展 resident 无对应量级增长。

### 风险
- GOMEMLIMIT 调小会抬升 CPU，按设备分档是为了兼顾老设备。
- 容量收紧可能让调试面板历史记录变少——这是诊断数据，可接受。

## 版本与交付节奏

| 期 | 内容 | 预期常驻收益 | 风险 |
|----|------|--------------|------|
| 一 | 分桶埋点 + 压力源 | 无直接收益，建立基线 | 极低 |
| 二 | 定时器合并 + 批量落盘 | CPU 降、常驻 NSData 副本减少 | 低（秒级延迟） |
| 三 | 压力自动降级 | 杜绝 jetsam | 中（需调阈值） |
| 四 | Go 配置 + 诊断结构容量上限 + 泄漏审计 | 长时稳态 | 中（需调阈值） |

每期独立可发版，补丁号自动进位；每期限定在扩展进程与 App Group 通信，不动主 App UI 既有逻辑。
